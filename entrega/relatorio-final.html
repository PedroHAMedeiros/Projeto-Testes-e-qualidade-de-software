1.4 Abordagem (estratégia)

  • Baseada em risco: o esforço segue a matriz da seção 1.5.
  • Pirâmide de testes adaptada: maioria na API (rápidos, estáveis, sem navegador), menos na UI, poucos E2E que cruzam o sistema inteiro. Testes de unidade não se aplicam: não temos o código do SUT em execução (ver seção 1.9).
  • Caixa-preta + leitura do código-fonte só para explicar causa de defeito já encontrado (análise de causa raiz), nunca para "adivinhar" testes.
  • Técnicas: particionamento de equivalência, análise de valor-limite, tabela de decisão (pagamento), testes negativos, testes exploratórios com charter, teste de contrato (status + formato), testes de caracterização (fixam o comportamento atual), mocks/stubs na UI, verificação cruzada UI ↔ API.
  • Defeitos conhecidos viram testes que esperam o comportamento correto e são marcados com test.fail() — a suíte fica verde, mas avisa quando o defeito for corrigido.

1.9.1 Justificativa das ferramentas e tecnologias

A escolha das ferramentas considerou os tipos de teste necessários, a facilidade de manutenção e a integração com o pipeline de CI.

Playwright: escolhido por permitir testes de API, interface e E2E utilizando a mesma ferramenta. Isso facilita o compartilhamento de recursos, reduz a necessidade de ferramentas adicionais e oferece mecanismos de espera automática, assertions com retentativas e captura de evidências. Selenium, Cypress e Postman também são alternativas válidas, mas o Playwright atende melhor à necessidade de centralizar os diferentes tipos de teste.

TypeScript: utilizado para estruturar a suíte e implementar recursos reutilizáveis. A tipagem ajuda a identificar inconsistências durante o desenvolvimento e facilita a manutenção de fixtures, clientes de API e Page Objects.

Chromium: definido como navegador de referência para padronizar a execução dos testes. Essa escolha, entretanto, limita a validação de compatibilidade a esse navegador.

ESLint: utilizado para identificar problemas de padronização e práticas inadequadas, mantendo a consistência do código.

jscpd: utilizado para identificar duplicações e reduzir redundâncias, facilitando futuras alterações.

GitHub Actions: responsável por automatizar a execução dos testes e da regressão, permitindo acompanhar resultados e gerar relatórios. Como o SUT é externo, as execuções também dependem da disponibilidade do serviço e de mecanismos de proteção, como o Cloudflare.

As ferramentas foram escolhidas de acordo com as necessidades do projeto. A solução busca integrar automação, análise de qualidade e execução contínua sem adicionar tecnologias desnecessárias.

1.9.2 Justificativa dos critérios de prioridade

A prioridade indica a urgência de correção do defeito, considerando o risco e o impacto no fluxo afetado.

  • P1 — Urgente: exige correção imediata devido ao risco relevante.
  • P2 — Alta: afeta regras de negócio, dados ou funcionalidades importantes.
  • P3 — Baixa: possui impacto mais limitado e menor exposição.

BUG-002 P2 Permite ultrapassar o limite de quantidade no carrinho, violando uma regra comercial.
BUG-003 P2 Permite adicionar produtos sem estoque pela API.
BUG-004 P2 Permite persistir e-mail inválido no cadastro.
BUG-005 P1 Aprova método de pagamento desconhecido, exigindo correção urgente.

A prioridade considera a urgência e o risco de correção, não apenas a existência do defeito.

4.3 Isolamento, dados, setup/teardown e sincronização

  • Independência: nenhum teste depende de outro nem da ordem. Cada um cria os próprios dados (usuário, carrinho), e por isso os testes rodam em paralelo (fullyParallel).
  • Setup por API, verificação pela UI: as pré-condições são criadas via API (rápido e confiável) e a UI só é usada no que está sendo testado. Exemplo: o E2E não testa o cadastro, que tem testes próprios.
  • Teardown: os carrinhos são apagados. As contas não podem ser apagadas pelo cliente (limitação documentada no doc 01 §1.8).
  • Sincronização sem esperas fixas: asserções com nova tentativa automática, waitForResponse para eventos de rede e expect.poll para estabilidade. A regra de lint playwright/no-wait-for-timeout proíbe waitForTimeout nos testes.
  • Tratamento de falhas: trace, vídeo e print guardados em toda falha; 1 nova tentativa por teste, contabilizada como flaky.

4.4 Por que não há cobertura de código — e o que medimos no lugar

Cobertura de código (linhas e ramos executados) exige instrumentar o servidor do SUT, que não é nosso. Medi-la sobre o código dos testes não diz nada sobre a qualidade do sistema. Por isso usamos três medidas honestas:

  1. Cobertura da superfície da API: operações do contrato OpenAPI exercitadas pela suíte (scripts/endpoint-coverage.mjs, que cruza as chamadas registradas durante os testes com o contrato baixado na hora).
  2. Cobertura de requisitos e riscos: matriz do doc 10 §10.2.
  3. Cobertura de técnicas: tabela 4.2.

O caminho para ter cobertura de código real seria subir o SUT localmente com o docker-compose.coverage.yml do repositório oficial (trabalho futuro, doc 08).

5.4 Proposta de evolução/correção — validação de pagamento por estratégia (corrige BUG-005)

Problema: PaymentController::check aprova qualquer método desconhecido (fail-open).

Proposta técnica:

  1. Contrato: payment_method obrigatório e restrito ao enum já documentado no OpenAPI → 422 com {"errors":{"payment_method":[...]}} para valores fora da lista.
  2. Implementação: um mapa método → validador (padrão Strategy). Cada validador declara suas regras (BankTransferValidator, CreditCardValidator, …). Método sem validador = erro, nunca sucesso (fail-closed).
  3. O endpoint passa a responder com o mesmo formato de erro dos outros (422 + errors).

Critérios de qualidade:

Critério Meta
Métodos fora do enum (incl. ausente, vazio, maiúsculas CREDIT-CARD) 100% rejeitados com 422
Métodos válidos com dados válidos 100% aprovados (sem regressão)
Cada regra de cada método coberta por ≥ 1 caso de tabela de decisão
Contrato OpenAPI × implementação 0 divergências no teste de contrato

Validação / estratégia de testes:

  • Os testes já existem: API-PAY-04 vira verde (remover test.fail()); API-PAY-01..03 garantem a não-regressão.
  • Acrescentar casos para payment_method ausente, "", null e com caixa diferente (particionamento).
  • Rodar E2E-01 com os 5 métodos pela UI (parametrizar o teste).
  • Gate no CI: a correção só entra com o pipeline verde.

BUG-001 — sort inválido em GET /products retorna HTTP 500

  • Descrição: valores de ordenação fora da lista suportada derrubam a requisição com erro interno em vez de serem rejeitados como entrada inválida.
  • Pré-condições: nenhuma (endpoint público).
  • Passos: GET /products?sort=foo,bar
  • Esperado: HTTP 400/422 com mensagem de validação (ou ordenação ignorada). Valores válidos documentados no contrato: name,asc|desc, price,asc|desc.
  • Atual: HTTP 500 {"message":"Something went wrong"}.
  • Evidências: evidencias/fase1-api/sondagem-api.log (linha "sort invalido"); teste API-PROD-13 (falha esperada) no relatório HTML.
  • Impacto: erro 500 polui monitoramento/alertas e indica que o valor chega à consulta SQL sem lista de permissão; facilita varredura automatizada por erros.
  • Causa provável (hipótese, não confirmada): o parâmetro é repassado a um filtro genérico ($query->filter() em ProductService::getAllProducts) sem validação de coluna.

BUG-002 — Limite de 99 unidades é burlado por adições sucessivas

  • Pré-condições: carrinho criado (POST /carts).
  • Passos: POST /carts/{id} com {product_id, quantity: 60} duas vezes; GET /carts/{id}.
  • Esperado: a regra quantity 1..99 (validada pelo próprio SUT em cada requisição — ver API-CART-02) deveria valer para a quantidade resultante; a 2ª adição deveria ser rejeitada (422) ou limitada a 99.
  • Atual: as duas retornam 200 e o item fica com quantity = 120.
  • Evidências: evidencias/fase1-api/limite-quantidade-acumulada.log; teste API-CART-08.
  • Causa (código): CartService.php faz $existingItem->increment('quantity', $quantity) sem verificar o total; a validação max:99 (CartController, linha 111) só olha o valor da requisição.
  • Impacto: pedidos com quantidades acima do permitido; regra de negócio inconsistente entre "adicionar" e "atualizar".

BUG-003 — API aceita produto sem estoque no carrinho

  • Pré-condições: produto com in_stock=false (no seed: "Long Nose Pliers").
  • Passos: POST /carts/{id} com o ID desse produto e quantity: 1.
  • Esperado: rejeição (422), coerente com a UI, que desabilita o botão "Add to cart" para esse produto (teste UI-CAT-08, print evidencias/fase1-exploracao/produto-sem-estoque.png).
  • Atual: 200 {"result":"item added or updated"}.
  • Evidências: evidencias/fase1-api/sondagem-api.log (linha "add out-of-stock"); teste API-CART-09.
  • Impacto: a regra existe apenas no front-end. Qualquer cliente da API (app móvel, integração, usuário com DevTools) compra item indisponível. Exemplo clássico de validação só no cliente.

BUG-004 — Cadastro aceita e-mail inválido

  • Passos: POST /users/register com dados válidos e email: "nao-e-email".
  • Esperado: 422 (a UI rejeita com "Email format is invalid" — teste UI-AUTH-05).
  • Atual: 201 Created com o usuário persistido.
  • Evidências: evidencias/fase1-api/sondagem-api.log (linha "register email invalido"); print da UI evidencias/fase1-exploracao/cadastro-email-invalido-ui.png; teste API-AUTH-10.
  • Causa (código): StoreCustomer.php, linha 67: regras ['required','unique:users,email','string','max:256', ...] — falta a regra email.
  • Impacto: contas que não recebem e-mail (recuperação de senha impossível), dados sujos.

BUG-005 — /payment/check aprova método inexistente

  • Passos: POST /payment/check com {"payment_method":"bitcoin","payment_details":{}}.
  • Esperado: 422 — o contrato OpenAPI declara payment_method como enum (bank-transfer, cash-on-delivery, credit-card, buy-now-pay-later, gift-card).
  • Atual: 200 {"message":"Payment was successful"}.
  • Evidências: evidencias/fase1-api/sondagem-api.log (linha "payment check metodo invalido"); teste API-PAY-04.
  • Causa (código): PaymentController::check (linhas 35–70) é uma sequência de if independentes, um por método, sem else/caso padrão; um método desconhecido não entra em nenhum ramo e cai direto no return ... 'Payment was successful' (linha 70). Também vale para payment_method ausente.
  • Impacto: a verificação de pagamento — o controle mais sensível do fluxo — falha "aberta" (fail-open). Por isso severidade Alta e P1.

BUG-006 — Idade máxima efetiva é 93 anos, não 75

  • Passos: POST /users/register com dob = hoje − 75 anos − 1 dia (ex.: 1951-11-19).
  • Esperado: 422 com "Customer must be younger than 75 years old." (contrato: "between 18 and 75 years ago").
  • Atual: 201. O limite real é 93 anos: 1933-11-21 → 201, 1933-11-20 → 422.
  • Evidências: evidencias/fase1-api/fronteira-idade-93-anos.log; testes API-AUTH-05b (falha esperada) e API-AUTH-05c (caracterização do limite real).
  • Causa (código): StoreCustomer.php, linhas 44–46: $dt = new Carbon(); $before = $dt->subYears(18)...; $after = $dt->subYears(75).... Carbon é mutável: subYears(18) altera $dt, e o subYears(75) é aplicado sobre a data já deslocada (18 + 75 = 93).
  • Impacto: baixo (público acima de 75 anos), mas é um ótimo exemplo de defeito que só a análise de valor-limite encontra — o caso típico (35 anos) nunca falharia.

BUG-007 — Checkout: a busca automática de CEP substitui, sem aviso, o endereço digitado ou salvo

  • Pré-condições: usuário autenticado, 1 item no carrinho, passo 3 do checkout ("Billing Address").
  • Cenário A (endereço digitado): país = Brasil; CEP 59000-000; número 100; logo em seguida digitar rua "Rua das Flores", cidade "Natal", estado "RN"; aguardar alguns segundos.
  • Cenário B (endereço salvo no perfil): cliente cadastrado com endereço "Rua das Flores, Natal, RN, CEP 59000000"; abrir o passo 3 e não tocar no formulário.
  • Esperado: o que o cliente digitou ou salvou é preservado. Uma sugestão da busca de CEP deveria preencher só campos vazios ou pedir confirmação.
  • Atual:
    • Cenário A: após a resposta assíncrona de GET /postcode-lookup, os campos são substituídos ("R. Horácio / Carmona d'Oeste / Santa Catarina") ou apagados. Em 3 execuções: 2 sobrescritas e 1 apagamento.
    • Cenário B: o formulário carrega o endereço do perfil (t ≈ 1 s: "Natal / RN"), a busca de CEP dispara sozinha e o substitui (t ≈ 3 s: "Júlio d'Oeste / Piauí").
    • Comportamento intermitente (depende da ordem das respostas assíncronas): a 1ª versão do teste chegou a passar na 1ª tentativa.
  • Efeito em dado persistido: na 1ª execução completa (20/11, 22:22Z) a fatura do E2E-01 foi gravada com billing_city = "Carmona d'Oeste", embora o teste tenha digitado "Natal". Na execução oficial 1 (22:45Z), o teste leu "Júlio d'Oeste" no formulário e a fatura saiu com "Carmona d'Oeste": o endereço mudou de novo entre a leitura e a confirmação.
  • Contexto técnico (código do SUT): ao criar a fatura, a API valida a cidade e o estado contra o próprio serviço de CEP (Rules/AddressMatchesCountry.php). A sobrescrita no front-end parece ser uma tentativa de "alinhar" o formulário a essa regra. Como o serviço de CEP é simulado (OBS-04) e inconsistente entre formatos (BUG-009), o cliente não tem como saber qual endereço vai valer.
  • Evidências: evidencias/fase3-exploratorios/SE-04-cep-console.log, SE-04-cep-sobrescreve-campos.json, SE-04-cep-execucao-{1,2,3}.png, observacoes-OBS-05-OBS-07.log, OBS-07-prefill-perfil.png, SE-04-postcode-formatos.log; teste UI-CHK-02.
  • Impacto: o pedido pode ser gravado com um endereço de cobrança diferente do que o cliente informou, sem que ele perceba, o que afeta um dado fiscal (fatura). Severidade Alta. Prioridade P2, e não P1, porque no ambiente de demonstração o serviço de CEP é simulado.

BUG-008 — GET /favorites/{id} devolve favorito de outro cliente

  • Pré-condições: dois clientes, A e B, autenticados; A tem um favorito.
  • Passos: B chama GET /favorites/{id-do-favorito-de-A} com o próprio token.
  • Esperado: 404 (ou 403). A listagem GET /favorites já filtra pelo dono, e o DELETE também.
  • Atual: 200 com {"id":…, "user_id": "<id de A>", "product_id": …}.
  • Causa (código): Services/FavoriteService.php::getFavoriteById() usa Favorite::findOrFail($id) sem where('user_id', Auth::id()), ao contrário de getAllFavorites() e deleteFavorite() no mesmo arquivo. É uma inconsistência dentro da mesma classe.
  • Evidências: evidencias/fase1-api/sondagem-api-2.log; teste API-AUTHZ-03.
  • Impacto: categoria API1 do OWASP API Security Top 10 (Broken Object Level Authorization). O dado exposto aqui é pouco sensível (ID do cliente e do produto), por isso Média, mas o mesmo padrão em outro recurso seria grave. Para comparação: as faturas estão corretamente protegidas (API-AUTHZ-06).

BUG-009 — Mesmo CEP, endereços diferentes conforme o formato

  • Passos: GET /postcode-lookup?country=BR&postcode=59000000&house_number=100 e o mesmo com 59000-000.
  • Esperado: mesmo endereço; o CEP é o mesmo e só muda a formatação.
  • Atual: 59000000 → "Júlio d'Oeste / Piauí"; 59000-000 → "Carmona d'Oeste / Santa Catarina". O resultado é estável para cada formato.
  • Evidências: evidencias/fase3-exploratorios/SE-04-postcode-formatos.log; teste API-CEP-02.
  • Impacto: baixo isoladamente, mas contribui para o BUG-007: o perfil guarda o CEP sem hífen e o cliente digita com hífen, e cada formato produz um endereço diferente.

8. Conclusões, Lições Aprendidas e Limitações

Neste trabalho, avaliamos o Practice Software Testing (Toolshop) usando testes manuais, exploratórios e automatizados. O objetivo foi verificar se as principais funcionalidades atendiam ao comportamento esperado, identificar defeitos e registrar evidências para justificar os resultados.

8.1 Conclusões sobre os testes

A estratégia de priorizar os testes pelos riscos foi importante porque direcionou a análise para funcionalidades que poderiam causar mais problemas ao usuário, como pagamento, carrinho e checkout. Foi nessas áreas que encontramos alguns dos defeitos mais relevantes, entre eles:

  • BUG-003: a API permite adicionar ao carrinho um produto sem estoque, embora a interface bloqueie essa ação.
  • BUG-005: a verificação de pagamento aceita um método que não existe.
  • BUG-007: o endereço informado pode ser substituído durante o checkout, afetando os dados da fatura.
  • BUG-008: uma requisição permite consultar um favorito pertencente a outro usuário.

Na execução oficial local, realizada em 20/11/2026, foram registrados 104 testes automatizados: 77 de API, 25 de interface e 2 E2E. Desses, 93 passaram diretamente, 2 passaram após nova tentativa (flaky) e 9 apresentaram falhas esperadas por defeitos já conhecidos. Não houve falhas inesperadas nessa execução.

A cobertura das operações de API incluídas no escopo chegou a 79,2% (38 de 48), superando a meta de 60%. Os resultados mostram que os testes de API foram especialmente úteis para encontrar problemas nas regras do sistema. Já os testes de interface e E2E ajudaram a verificar o que acontece na prática durante o uso. No caso do BUG-007, por exemplo, foi importante conferir os dados da fatura no back-end, e não apenas o que aparecia na tela.

Mesmo com esses resultados, não podemos dizer que o sistema está livre de falhas. Os nove defeitos identificados continuam documentados e ainda não foram corrigidos na aplicação testada.

8.2 Critérios de saída

Ao comparar os resultados com os critérios definidos no plano de testes, observamos que:

  • A execução local atingiu a meta de zero falhas inesperadas na regressão automatizada.
  • A taxa de testes flaky foi de 1,9% (2 de 104), abaixo do limite de 5%.
  • A cobertura de operações de API em escopo (79,2%) superou a meta de 60%.
  • Os 9 defeitos confirmados possuem registros, evidências e testes associados.
  • O pipeline do GitHub Actions foi implementado, mas sua validação remota ficou parcial, pois o Cloudflare bloqueou parte dos testes de interface e E2E. A solução para identificar esses bloqueios foi validada localmente, mas a documentação ainda apontava uma nova execução no GitHub como pendente.

Além disso, a documentação indica que a execução manual dos casos e as sessões exploratórias feitas diretamente pela equipe ainda precisam ser concluídas e registradas. Por isso, consideramos que os objetivos técnicos da automação foram alcançados em boa parte, mas nem todos os critérios de encerramento do projeto foram atendidos.

8.3 Lições aprendidas

Um dos principais aprendizados foi perceber que um teste aprovado nem sempre significa que tudo está correto. Alguns problemas só apareceram quando verificamos a resposta da API ou os dados que realmente foram gravados, em vez de confiar apenas na interface.

Também vimos a importância de conferir os próprios testes. Durante o desenvolvimento, um teste com mock chegou a passar sem verificar corretamente o cenário esperado. Isso mostrou que uma asserção mal construída pode dar uma falsa sensação de segurança.

Outra dificuldade foi trabalhar com um sistema público, fora do nosso controle. Houve lentidão, mudanças nos identificadores dos produtos (re-seed) e bloqueios de acesso no ambiente de CI. Foi necessário adaptar os testes para buscar dados atualizados, esperar pelas respostas corretas e distinguir problemas do ambiente de defeitos reais da aplicação.

Por fim, entendemos que testes automatizados e exploratórios se complementam. A automação ajuda a repetir os cenários e acompanhar regressões; a exploração ajuda a encontrar situações que ainda não tinham sido previstas. Os resultados precisam ser analisados, e não apenas contabilizados.

8.4 Limitações

O trabalho teve algumas limitações que devem ser consideradas ao interpretar os resultados:

  • Ambiente compartilhado: não controlamos os dados, as atualizações nem a disponibilidade do sistema testado.
  • Cobertura: os 79,2% correspondem às operações de API em escopo, não à cobertura do código-fonte da aplicação.
  • Navegadores e dispositivos: a automação da interface foi realizada no Chromium, sem uma avaliação completa em outros navegadores ou dispositivos móveis.
  • CI/CD: o Cloudflare impediu a execução remota de parte dos fluxos de interface e E2E.
  • Correção dos defeitos: os problemas foram registrados, mas não alteramos o código do sistema testado.
  • Execução manual: os casos MT-05, MT-10, MT-11 e MT-14 não foram executados (ver a rastreabilidade do projeto).

Essas limitações não anulam os resultados, mas deixam claro até onde as conclusões podem ser aplicadas.

8.5 Considerações finais e melhorias futuras

De modo geral, o projeto permitiu aplicar técnicas de teste, acompanhar defeitos e avaliar a qualidade de um sistema real. A combinação de testes de API, interface e E2E trouxe uma visão mais completa do que seria possível usando apenas uma dessas abordagens.

Se o trabalho fosse ampliado, os próximos passos seriam executar os testes em um ambiente local controlado, ampliar a cobertura para outros navegadores, concluir as atividades manuais da equipe e validar novamente o pipeline no GitHub Actions. Também seria importante encaminhar os defeitos aos responsáveis pelo sistema e repetir os testes depois das correções.

Não recomendaríamos liberar a versão avaliada sem antes tratar os defeitos de maior impacto, principalmente os relacionados a pagamento, estoque e endereço. A principal conclusão é que testar não consiste apenas em obter resultados positivos: também é necessário entender os riscos, verificar as evidências e reconhecer o que ainda não foi validado.
